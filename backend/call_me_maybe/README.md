# Call Me Maybe

## Description

This project converts natural-language requests into structured function
calls. For each prompt, the program chooses one function from the supplied
function definition file and extracts typed parameters that match the selected
function prototype.

The output is a JSON array where each item contains exactly:

- `prompt`: the original user prompt
- `name`: the selected function name
- `parameters`: a JSON object containing all required arguments

## Algorithm Explanation

The function name is selected with prefix-constrained decoding.

1. The program builds a function-calling prompt containing the available
   function definitions.
2. For every possible function name, it computes the token sequence that would
   be generated after the current prompt.
3. At each generation step, it asks the LLM SDK for next-token logits.
4. It keeps only token ids that continue at least one valid function-name
   prefix.
5. It chooses the legal token with the highest logit.
6. As soon as the generated token sequence exactly matches one function name,
   decoding stops and that function is selected.

This means the LLM still decides by logits, but it can never emit a function
name outside the supplied tool list.

After a function is selected, parameter extraction is constrained by the
function prototype:

- every required argument name from `args_names` is emitted;
- values are cast according to `args_types`;
- numeric arguments are extracted and cast to `int` or `float`;
- boolean arguments are normalized to `bool`;
- string arguments are extracted from quoted text or prompt context;
- the regex substitution helper recognizes common requests such as digits,
  vowels, and replacing one quoted word with another.

The final JSON is produced from a Pydantic output model, so the generated file
keeps the required top-level schema.

## Design Decisions

The code is kept in a small number of modules:

- `selector.py`: function-name selection and constrained token decoding
- `extractor.py`: prototype-aware argument extraction and casting
- `parser.py`: JSON input and output handling
- `__main__.py`: command-line flow from input files to output JSON

The LLM SDK is imported lazily. If the local machine does not have the heavy
model dependencies installed, the program prints a warning and uses a fallback
selector so the rest of the JSON pipeline can still be tested. With the SDK
installed, function selection uses the constrained LLM path.

## Performance Analysis

The constrained selection step only compares the small set of available
function names, so each generated token considers a limited legal token set.
For the provided input size, the non-model parts run almost instantly. Model
runtime depends on whether Qwen/Qwen3-0.6B is already downloaded and on the
available device.

Reliability comes from separating structure from free-form generation:

- function names are limited to valid candidates;
- output keys are generated by code, not by prompting;
- parameter names come directly from the function definition;
- values are cast before writing the JSON file.

## Challenges Faced

The main challenge is that small LLMs are unreliable at producing exact JSON.
The solution avoids asking the model to write JSON directly. Instead, it lets
the model choose only among valid next tokens for the function name, then builds
the JSON object in Python.

Another challenge is string extraction. For example, a prompt can contain an
apostrophe inside a quoted string, such as `I'm`. The extractor handles this by
using prompt context like `in the string ... with ...` instead of relying only
on simple quote splitting.
